# Canvas Escape native-readiness evidence

PR #443 first failed its head CI at `6b1bec2a77e6c8286c48b29e68cfa030b221877c` when the main pane stayed hidden after guest Escape in `e2e/canvas.spec.ts`. Five unchanged local repetitions passed and one controlled head retry passed 478 desktop cases with four skips and seven site cases. Protected queue run [40992737267](https://github.com/TypeSafeAI/modex/actions/runs/40992737267), job `123858729561`, then repeated the same failure at line 224: 477 desktop passes, four skips, one failure; site tests did not run. Both first failures and traces remain preserved. No second blind retry was requested.

A controlled diagnostic held the main-process `canvas:show` calls carrying `fullView: true`. The renderer's main pane became hidden while those calls remained pending. Guest `before-input-event` observed Escape while native full-view state had not been applied, and the main pane stayed hidden. After releasing the calls, another Escape arrived with full view applied and restored the main pane. This establishes that the old renderer-hidden assertion alone does not prove native readiness. The hosted traces lack the main-process event ordering needed to attribute those specific failures conclusively.

A second controlled check observed native guest visibility and geometry. The condition was false while the full-view calls were held, became true after they were applied, and Escape then restored the main pane (one pass, 5.5 seconds). The candidate waits until the visible native guest matches the renderer preview bounds, accounting for zoom and one-pixel rounding, before sending the same single Escape. Five unchanged candidate repetitions passed in 49.5 seconds. External-request refusal, privileged navigation refusal, popup refusal, main-pane restoration and guest-destruction assertions remain intact. No sleep, input retry, timeout increase or production change is introduced.
