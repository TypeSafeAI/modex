# iPhone trust observer startup recovery

The paired iPhone job for PR #524 at signed `ff353c0c0900ee4090985f897ba4e44e65c55d7f` failed before its Mac thread appeared. Its immutable artifact passed API size/digest and ZIP checks. Native xcresults retain 65 passes; paired xcresults retain 42 passes, one expected-failure control and one actual failure. The recording shows “Connection issue — The request timed out.” App diagnostics record callback-enter and chain-start without chain-return, and the system archive records the same app entering Security trust evaluation with a matching trustd peer. These observations localize the blocked certificate-chain read, but do not establish its underlying cause or a product TLS repair.

The observer itself stopped after its first five-second booted-device metadata query. Its manifest records COMMAND_TIMEOUT without the common unconfirmed-cleanup marker. The existing bounded-command implementation distinguishes a closed timeout from unverified closure; the new recovery relies on the actual `closed === true` result for every retry rather than assuming closure from an error name. It makes at most three sequential reads of the same booted-device metadata, retaining the same five-second and one-MiB command limits and the existing fifteen-minute observer deadline. Non-timeout errors, cancellation, malformed metadata, the wrong/not-booted device and unconfirmed closure remain terminal. A success racing cancellation cannot confirm startup. Receipts retain fixed outcome/error classes per attempt and no raw command output or error text.

The explicit CI/Debug device guard, app image/process birth checks, callback/thread/activity and trustd-peer binding, sample bounds and common cleanup stop gate remain unchanged. Direct command closure still does not prove simulator-side descendant cleanup or atomic native identity. This change retries only diagnostic startup reads; it does not retry pairing, change test outcomes, alter trust APIs/pins/request deadlines, modify OS preferences or admit a runtime.

The existing focused baseline passed 25 cases. Seventeen new bootstrap controls cover successful metadata, one/two closed timeouts, budget exhaustion, unclosed/unknown closure, non-timeout errors, pre/post-command cancellation, wrong device, malformed data, successful-but-unconfirmed closure, invalid identifiers and private error strings. The cancellation-success race first failed with a missing rejection and then passed after the post-command abort check. The final combined run passed all 42 cases with no skips or failures. The initial missing-helper RED and one test-fixture correction are retained separately; full root validation, scoped review and hosted diagnostic collection retain their own receipts.

Evidence is retained outside the worktree in the session’s `modex-closeout` directory: `pr524-ff353c0-iphone-first-failure-proof.json`, the verified archive and extracted xcresults/recording/diagnostics, `ios-trust-bootstrap-baseline.log`, `ios-trust-bootstrap-red.log`, `ios-trust-bootstrap-abort-race-red.log` and `ios-trust-bootstrap-final-focused.log`. No acceptance checkbox, physical-phone/older-Companion/two-LAN gate, release or activation decision changes on these observations. A future successful pairing alone must not be described as a repair of the original trust stall.
