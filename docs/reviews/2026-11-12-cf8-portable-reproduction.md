# Portable CF-8 retention reproduction

The opt-in [benchmark procedure](../../apps/desktop/bench/README.md) reproduces #281’s archived repeated history/log shapes from explicit source revisions. It prepares and verifies both exports before launching twelve fresh Electron apps, using existing synthetic CLI fixtures with no real inference or execution of the command shown in the transcript. It retains the seeded homes, repositories, generated drivers, source/build manifests, first logs and observations in a new private output directory. Ordinary E2E fixture cleanup is unchanged.

## Review, failures and reproducibility boundaries

Fresh independent review of implementation `545e9968` found two Important issues: worker cleanup removed seeded inputs, and the desktop’s actual resolved core was insufficiently bound. A third finding was raised from Minor to Important after a control proved that a matching-byte symlink could select an unbound relative import. All three received failing regressions before repair in one coalesced pass. The repaired source retains benchmark inputs using a seed-only private temporary root restored before app launch, binds actual core metadata/entry before building and launching, and rejects noncanonical, missing, traversing or symlinked driver paths. The review was source review with validation pending; the subsequent full qualification above verifies the repaired source, without a second review or an invented approval.

The original `545e9968` full qualification stopped before measurement when two unchanged unit cases exceeded their 6-second Stop and 5-second demo deadlines. Both passed unchanged in a separately recorded focused control; the timing cause remains unestablished. That failed qualification and its first logs are retained. The later run was justified by the actual review repairs, passed the entire suite and invoked the twelve-case benchmark once. A deliberate pre-measurement review hold on the first run was never reached. Earlier setup failures involving an unnecessary dependency-free core directory and a wrong typecheck working directory are also retained; neither was a measured app failure. No automatic retries were used.

The README explicitly fetches both full comparison SHAs, since fresh `main` clones may lack the pre-squash head. A separate fresh bare-repository control fetched both exact commits successfully; this tests source availability, not a second complete installation or measurement series. The CLI refuses unavailable/short refs, existing outputs, dangling links, divergent/dirty common core, traversal, changed source/build/driver bytes and changed dependency links. A failed worker retains its seeded input locator before other setup. Preparation and measurement stop at the first failure and never delete or overwrite an earlier run.

Review boundaries remain explicit: the owned diagnostic trusts developer Git/PATH/Node configuration, does not attest every third-party dependency or Electron byte, and does not provide atomic protection against a hostile concurrent filesystem writer. Standalone verification checks listed bytes against supplied metadata; orchestrated use also binds the recorded manifest digest. Power loss, forced termination and disk exhaustion can leave incomplete receipts, which cannot satisfy the twelve-case completion gate. Original workload errors remain in per-case receipts even if teardown surfaces a later close error. Two archived fixture files intentionally preserve their original extra EOF blank lines, so full-branch `git diff --check` reports those two cosmetic warnings. Ordinary local UI E2E was not repeated for tooling-only changes; required hosted and protected-queue checks remain delivery gates.

This procedure supplies portable repeated-series measurement tooling for the combined reproducible capture/performance criterion. It does not complete #281’s visual-difference inventory, real-provider/native/platform/device/human acceptance, child issue gates, rollout or release. S5’s existing literal acceptance and its original numeric receipt remain separate. No new issue box is checked by this tooling receipt, and Code Review/LocalExecution defaults and admission remain unchanged.
