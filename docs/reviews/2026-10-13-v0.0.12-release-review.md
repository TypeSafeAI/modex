# v0.0.12 release preparation

Desktop v0.0.12 prepares signed macOS update installation and native Windows/Linux
installers on the recovered source. Publication remains pending. The published
[v0.0.11 release](2026-10-12-v0.0.11-release-review.md) includes Canvas but deliberately
excludes the updater and publishes only macOS installers.

This preparation starts from protected main
`51385378a2d2f6536e8cb65377ceb7d25877e35e` (#190). It changes the desktop version and
release records. Website download fallbacks remain on published v0.0.11. Companion
build 6 and its Apple distribution records are separate from this desktop candidate. Before
landing, the preparation incorporates current main `575d310` (#192), which corrects the
current Haiku alias.

## Candidate behavior and compatibility

- Interactive Canvas retains HTML, SVG, and Markdown previews, file refresh, full view,
  and browser isolation from #164.
- The updater from #181 verifies downloads and the publisher, reports progress, and
  coordinates restart with active turns and unsaved work. Schema-2 drafts preserve text,
  attachments, pending originals, and uncertain native-update state. Unknown or corrupt
  recovery data is preserved; restart does not silently resend a pending message.
- Native Windows x64 NSIS and Linux x64 AppImage/Debian installers use the platform CLI,
  PTY, and encrypted-storage paths from #173. Windows signing is deferred. Windows and
  Linux updates remain manual.

If you run published v0.0.11 or earlier, install the first updater-enabled release
manually. Automatic installation applies to subsequent supported packaged-Mac updates
after signed native acceptance. The private `0.0.0` upgrade fixture uses the same source
as its candidate; it does not prove migration from a published historical build.

The planned draft contains five installers, `SHA256SUMS.txt`, and
`RELEASE-MANIFEST.json`. The [release workflow](../release-signing.md#cutting-a-release)
binds their bytes to the exact signed tag, source, run, and native reports. It excludes
private fixtures, refuses existing public releases or populated drafts, and does not
publish automatically.

## Release gates

1. Land the verified v0.0.12 preparation through a signed commit, review, current-head
   checks, and protected squash. Select that exact source for the signed tag review.
2. Obtain the required tag approval and `release-signing` environment review. Run
   signing, notarization, stapling, and packaged E2E on GitHub-hosted macOS.
3. Pass native upgrade, native download failure, and interrupted-download scenarios on
   three separate hosted macOS runners using the exact signed source and candidate ZIPs.
4. Run Windows/Linux jobs on that same tagged source. Verify their installer manifests,
   installed-app reports, and candidate hashes. Current reports retain
   `installerAcceptance: pending`; successful smoke checks do not establish authenticated
   Claude/Codex account operation, KWallet6, or a full graphical/PAM login session.
   Complete or explicitly disposition these checks during release review.
5. Independently verify the draft downloads, checksums, source/version/run identity,
   macOS signatures, Gatekeeper, stapled tickets, and native receipts. Record remaining
   limits and obtain publication approval before publishing; then verify public assets.

No signed tag, signing approval, native macOS updater run, draft upload, or publication
is established by this preparation. Physical iPhone and human VoiceOver acceptance
remain separate tracks.

## First tagged run

Val chose two conditions for publishing v0.0.12:
- Publish macOS installers only. The workflow still builds and checks the Windows and Linux
  candidates, but they stay off the public release.
- Ship automatic installation only if all three signed native updater scenarios pass.

The preparation session stopped at the tag-approval gate. Its squash `e3fecf0` (#194) has tree
`e18d8eb`, identical to the tested PR head `f226e9f`. It received the signed tag `v0.0.12` on
2026-10-13.

**Post-merge CI on `e3fecf0`.** Main's push CI failed one Store test:
`store-desktop.spec.ts:150` (the `browser-tools` variant). Its composer read empty after host
recovery; 273 other tests passed.
- The job's rerun passed, and 15 local repeats on `e3fecf0` passed.
- The same tree passed both PR runs, and the next main commit passed.
- The test fills the composer within the same 0.1 s as ⌘⇧B opens a new browser tab, so this is
  recorded as a test race. It is not counted as product evidence.
- The test now waits for the new tab's address field to take focus and checks the draft before
  disconnecting. All four variants passed four repeats each.

**[Release run 38437820616](https://github.com/TypeSafeAI/modex/actions/runs/38437820616).**
- Signing, notarization, stapling and the packaged E2E suite passed, as did the native Windows
  and Linux candidate jobs.
- All three signed native update scenarios failed after about four minutes each, so attachment
  was skipped and no draft was created.
- In each scenario, the signed `0.0.0` source refused the tampered candidate download, as
  intended.
- Each then reported "The update could not be downloaded or verified" for the authentic
  candidate ZIP: 131,698,006 bytes, SHA-256
  `a1156e6d5111128eb340c19330298e9d870a1ccc3d3389cd3b6b94c9e3c0bd00`.

**Root cause.** Inside Electron, staging failed with `Invalid package
…/Modex.app/Contents/Resources/app.asar`. Electron's `fs` treats any path ending in `.asar` as an
archive to read, and every real Modex update contains that file.
- Running the shipped staging inside the run's signed `0.0.0` fixture app reproduced the error.
- In plain Node, the same staging and publisher verification accepted the same bytes, and each
  `codesign`, `PlistBuddy`, `lipo` and `spctl` step passed (`source=Notarized Developer ID`).
- No earlier test ran staging inside Electron: unit tests run in Node, and the updater UI tests
  substitute staging.

**Fix.** Staging now uses Electron's unpatched `original-fs` inside Electron.
- `e2e/update-archive-electron.spec.ts` stages an archive containing `app.asar` inside Electron.
  It failed with the production error before the fix.
- Inside Electron, the fixed staging and the real publisher verification accepted the run's signed
  candidate ZIP and removed the staging directory.
- Native Squirrel replacement was not exercised locally, because it shares state with the installed
  Modex. The hosted scenarios cover it.

The next tag must repeat every gate on the fixed source. No Modex build has been published with
automatic installation, so no installed copy carries this defect.

## Second tagged run

Val approved replacing the unpublished tag, so `v0.0.12` was re-signed on `a4383ff` (#200, which
includes #199). Main CI on `a4383ff` passed before approval.
[Release run 38449736915](https://github.com/TypeSafeAI/modex/actions/runs/38449736915) ran two
attempts.

**Attempt 1.** Packaged E2E failed one test:
`browser-document.spec.ts:274` "native login labels use Streamer toggle during pending CLI listing
from true". It received `TOKEN=[redacted]` where it expected the unmasked label.
- The main process reads Streamer Mode from the window with a 250 ms timeout and masks when the
  answer is late, so the failure erred toward masking.
- Both variants passed 10 local repeats each.

**Attempt 2.** Re-running the failed job rebuilt, re-signed and re-notarized the same source.
Signing, notarization, stapling and packaged E2E passed.
- **The real signed upgrade scenario passed.** The `0.0.0` source refused the tampered ZIP,
  authenticated the real one, refused to restart while Settings was open, then installed through
  Squirrel. It relaunched as 0.0.12, and that launch restored the draft and accepted further edits.
- **The native-failure scenario failed at a harness step.** Escape did not close Settings within
  5 s. Each refused install briefly marks the workspace (Settings included) inert while the
  renderer prepares, and Settings ignores Escape until the ready state reaches the window. The
  passing `e2e/update-preflight.spec.ts` waits for that inert state to clear before pressing
  Escape; the harness did not.
- **The interrupted scenario passed its product checks and failed a harness assertion.** After
  the source was killed mid-download, the reopened `0.0.0` showed recovery with the draft
  read-only and refused another install. The harness expected that refusal to match
  `/not ready|recovery/`. During startup recovery, every refused request carries the recovery
  message instead: "The update to Modex 0.0.12 has not been confirmed. Your saved drafts are
  preserved. Quit Modex, then reopen it…". Its `thread:create` check would have failed the same
  way.

**Harness fix.** The harness now waits for Settings to leave the inert region before pressing
Escape, as the e2e test does. During startup recovery, it requires that exact message for both
refusals. No product code changes. The harness refuses to run outside GitHub-hosted runners, so
the next tag is its verification.
